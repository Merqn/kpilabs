# Аудит sequence-діаграм Завдання 3

## Узгодженість із Gherkin-сценаріями

| Сценарій | Основні кроки діаграми | Підтвердження |
|---|---|---|
| S1 | Автентифікація, створення `Playlist`, перевірка `Track`, запис `PlaylistTrack` на позиції 1 | Відповідає Then-застереженням S1 |
| S2 | Перевірка власника, пошук треку, розрахунок `max(position) + 1` | Відповідає S2 |
| S3 | Пошук за складеним ключем і відмова при дублікаті без запису | Відповідає S3 |
| S4 | Перевірка `Playlist.user_id` і повернення HTTP 403 | Відповідає S4 |
| S5 | Перевірка каталогу і повернення «Трек не знайдено» | Відповідає S5 |

## Учасники та модульна відповідність

- `Слухач` відповідає актору зі Завдання 2.
- `PlaylistAPI` і `PlaylistService` координують use case.
- `AuthService` перевіряє автентифікацію та зв'язок користувача з плейлистом.
- `CatalogService` опрацьовує сутність `Track`.
- `PlaylistRepository` і `Database` працюють із `Playlist`,
  `PlaylistTrack` та зовнішніми ключами ER-моделі.

## Топ-3 розбіжності

1. Gherkin не показує внутрішні перевірки автентифікації й власності. Додано
   `validateUser()` і `validateOwner()` для узгодження з FR-06 і NFR-1.
2. Для S2 явно показано пошук записів і розрахунок `max(position) + 1`,
   щоб усунути неоднозначність наступної позиції з попередньої роботи.
3. Для помилкових гілок додано `alt` і конкретні return-повідомлення:
   HTTP 403, HTTP 404 і HTTP 409.
